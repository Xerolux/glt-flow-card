# Feature Landscape

**Domain:** Home Assistant-based GLT/BMS/SCADA visualization and engineering platform
**Project:** GLT Flow Card v1.1 Production-Ready GLT Platform
**Researched:** 2026-08-31
**Mode:** Brownfield production-hardening of all 30 requested capabilities
**Overall confidence:** MEDIUM — recommendations are cross-checked against current official standards, Home Assistant documentation, and current professional BMS product documentation; exact regulatory or site acceptance remains project-specific.

## Differentiators

These are valuable only after the table-stakes behavior above is true.

| Feature | Value Proposition | Complexity | Notes |
|---------|-------------------|------------|-------|
| Explainable semantic auto-mapping | Reduces engineering effort while keeping the engineer in control and creates auditable mapping evidence. | High | Confidence and reasons matter more than the number of auto-bound entities. |
| Profile-driven operations from one model | Lets symbols, controls, alarms, ports, diagnostics, and reports share one equipment contract instead of drifting configuration. | High | Requires schema/profile versioning before breadth expansion. |
| Safe simulation plus evidence-based commissioning | Allows offline engineering and repeatable fault scenarios without physical-bus writes, then turns the same contract into read-only commissioning checks. | High | Simulation isolation is a hard security boundary. |
| Semantic operations from plant to portfolio | Preserves alarm/trend/time context through equipment drill-down and multi-site roll-up. | High | Depends on honest freshness, permissions, and partial-data semantics. |
| Open, versioned extension ecosystem | Enables third-party symbols/profiles/panels/languages without modifying the core bundle. | High | The SDK must not become an unreviewed privileged-code channel. |

## Anti-Features and Claims to Avoid

| Anti-Feature / Claim | Why Avoid | What to Do Instead |
|----------------------|-----------|--------------------|
| “Certified SCADA,” “safety system,” or fire/security/life-safety control | The project is a Home Assistant visualization/engineering layer and has no stated safety certification or validated safety lifecycle. | State the non-safety boundary prominently and require separate certified systems for safety functions. |
| Native BACnet, KNX, Modbus, OPC UA, SNMP, or IEC driver claims | Fieldbus drivers are explicitly out of scope and provenance does not equal protocol implementation. | Show traceable Home Assistant integration/device provenance and communication health; keep HA integrations as protocol layer. |
| Browser-enforced roles or editable project ACLs described as security | The client can be modified and project content is caller-controlled. | Make the Companion policy authoritative for every sensitive read/write/control and test cross-user denial. |
| “Successful command” when only a service call was queued | Home Assistant service acceptance is not equipment readback or physical success. | Report accepted, failed, timed out, and verified-readback as separate states. |
| Alarm lifecycle based on UI rows, with shelving recorded but not enforced | This creates missed/duplicate alerts and a dangerous false sense of suppression. | Use one backend state machine with tested suppression, persistence, notifications, and restart recovery. |
| “Historian” for in-memory arrays or unqualified Recorder access | Retention, exclusions, quality, aggregation and reproducibility are not guaranteed. | Call it Recorder-backed trends unless durable historian acceptance passes; expose coverage and provenance. |
| “Report” for current KPI snapshots | A snapshot is not a period report and cannot reproduce alarm, maintenance, or energy history. | Persist report definitions, bounded periods, inputs, coverage, calculations and output warnings. |
| “True multi-site” for site filters or sequential remote REST calls | Filtering local config does not provide remote health, failure isolation, scalable state flow, security, or audit. | Require per-site health/freshness, bounded concurrency/subscriptions, partial results and remote authorization tests. |
| “300+ symbols” based on aliases, colors, styles, or untested combinations | Count inflation does not establish semantic correctness or operability. | Publish a generated unique catalog and visual/state/profile compatibility evidence. |
| Auto-mapping that silently writes bindings | Naming is ambiguous and incorrect controls can be hazardous. | Rank, explain, preview, explicitly accept, undo, and retain manual overrides. |
| Simulation mixed with live state/service paths | A test action can become a real plant command. | Use a separate provider and hard-block every local and remote write while simulation is active. |
| Commissioning that writes to plant by default | Physical writes exceed the repository-development approval boundary and may affect real equipment. | Default to read-only diagnostics; require separate explicit approval and bounded targets for any live test. |
| Plugin SDK as arbitrary script injection into privileged operations | It bypasses compatibility, authorization and supply-chain boundaries. | Namespace and validate UI extensions; require separately installed/reviewed backend code for privileges. |
| “Audit-grade” or “tamper-evident” for mutable local JSON/client events | Server timestamps alone do not provide immutability or integrity. | Call it an activity/audit log, distinguish client telemetry, and claim tamper evidence only after implementing and testing an integrity model. |
| “Collaboration locks” that saves do not enforce | Advisory UI locks do not prevent lost updates. | Atomically enforce revision plus lock token and provide conflict recovery. |
| “Internationalized” because DE/EN strings exist | Hardcoded strings, locale-insensitive values, broken plurals/RTL and backend key failures remain. | Validate complete catalogs and locale behavior across frontend/Companion. |
| “Accessible/mobile/kiosk-ready” based on responsive CSS | It does not prove keyboard, focus, screen-reader, touch target, reflow, critical-status, or security behavior. | Test complete operational and engineering workflows on assistive tech and real viewport classes. |
| “2,000-object support” based on a pure function timing | It does not execute DOM/SVG rendering, updates, routes, editor actions, persistence, history, or backend load. | Publish only capacity demonstrated by reproducible browser/backend scenarios and stated budgets. |

## Milestone Recommendation

All 30 features are required, but production-hardening should be ordered by dependency and risk:

1. **Truth and security foundations:** 23-27 plus 3 and the release portion of 30.
2. **Authoritative operations:** 1-6, including the alarm transition matrix and server-mediated controls.
3. **Semantic engineering core:** 7-13, with profile/version contracts before symbol-count expansion.
4. **Operational analysis:** 14-20, grounded in explicit Recorder coverage and reproducible reporting.
5. **Portfolio and ecosystem:** 21-22, after local authorization, provenance and failure semantics are proven.
6. **Product-wide usability and evidence:** 28-30 integrated throughout, with final mobile/kiosk/a11y/load claims only after executable gates pass.

The milestone should not defer any numbered area, but it should label a capability experimental until its row-level acceptance behavior is executable and passing.

## Research Gaps

- Exact plant/operator alarm philosophy, priority matrix, escalation timing, retention, and acknowledgement rules must be defined per deployment; ISA/OPC provide models, not the site policy.
- Home Assistant does not itself turn this card into a certified historian, CMMS, energy-management system, or safety system. Claims must stay bounded to implemented/tested integration behavior.
- Performance budgets for 100/500/2,000 objects, entity update rates, site counts, historian ranges, and concurrent designers require measurement on representative Home Assistant/browser hardware before numeric support claims are published.
- Whether one GitHub repository can provide a smooth one-click HACS experience for both the dashboard plugin and Companion needs a release/install design decision and validation against the actual chosen HACS distribution model.
- Full Haystack or Brick conformance is not required by the project today; if claimed later, add export and ontology-validation acceptance rather than relying on similar terminology.
