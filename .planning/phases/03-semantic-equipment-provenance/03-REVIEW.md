# Phase 03: Code Review Report

**Scope.** `equipment_profiles.py`, `provenance.py`, `semantic_model.py`,
`ws_provenance_get`, `src/v100/semantic-model.mjs`, `entity-mapping.mjs`,
`equipment-state.mjs`, schema 3 and its generated validators, and the 2→3
migration.

## Summary

No defect found. Two of this phase's guarantees are enforced *structurally*
rather than by convention, which is the distinction the Phase-2 pass showed
matters:

**A profile cannot name an effect** (T3-07). `FORBIDDEN_CONTROL_FIELDS` and the
closed `PROFILE_SECTIONS` tuple mean a profile that grows a `service` or a
`target` is rejected because the *shape* is closed, not because a reviewer
remembered the rule. A profile authored next year is covered by the same check.

**Trust outranks activity** (T3-06, T3-11). `STATE_PRECEDENCE` is a frozen
15-entry table whose first three entries are `communication_error`, `invalid`
and `stale`, so a datapoint the card cannot vouch for is never reported as
running, however recently it said so. Crucially, `test/equipment-state.test.mjs`
declares **its own copy** of the table and compares the module against it, then
asserts every untrustworthy state outranks every activity state. A test that
imported the module's table and asserted it equalled itself would pass on any
reordering; this one does not.

**Provenance is not a registry search** (T3-05). `ws_provenance_get` describes
only entity ids the *project* already references. The route is declared
`opaque` and project-scoped, so an unauthorized caller is denied by the boundary
before the handler runs, and an authorized caller cannot use their own project
as a lens onto the entity registry.

## Class-level sweeps

The Phase-2 pass found a defect that had been fixed at one instance and left at
three others. Both sweeps it produced were run across the whole Companion, not
just this phase:

1. **Filtered routes that do not filter their rows.** Phase 3 declares no
   `enumeration="filter"` route. `provenance/get` is `opaque` and correctly so:
   unlike a listing there is no honest partial answer to "describe this entity".
2. **A limit applied before filtering**, which turns a page size into a count
   oracle for rows the caller cannot see. Every handler in the component that
   takes a `limit` filters first — checked mechanically across
   `alarms/list`, `schedules/list`, `history/series`, `history/statistics` and
   `audit/list`. `ws_provenance_get` bounds `entity_ids` before filtering, which
   is the opposite order and the right one: the list being bounded is the
   *caller's own*, so slicing it reveals nothing they did not send, and bounding
   the work before doing it is what T3-12 asks for.
