# 10-01 — The gate, and the ledger this phase can get wrong while passing

Derive everything from a single `PHASE` constant. The gate's own docstring
records that literals-that-should-be-derivations caused three residual bugs in
earlier gates; do not reintroduce them.

**The ledger question for this phase is different from every previous one.**
Phase 7's was a query exceeding its bound, Phase 8's an effect reaching plant
during a rehearsal, Phase 9's a socket opened while proving a bound. Phase 10's
is **a measurement that measured nothing** — a capacity scenario that finishes
in three milliseconds because it built no objects, reported as a budget pass.

So the effect line for capacity carries the object count actually built, and the
test asserts it against the scenario's declared size. A scenario claiming 2,000
objects that built 0 fails.

## Steps

1. `tools/verify-phase10.mjs` deriving from `PHASE = 10`, with the focused
   commands (build, node, python, exact-dist, docs) and the Phase-9 gate.
2. `package.json`: `test:phase10`, `test:phase10:release` composed from the same
   leaves the other phases use. Do not invent a new release leaf.
3. `test/fixtures/phase10-effects.mjs`: the `PHASE10_*_EFFECTS` emitter, with the
   object-count field and the assertion that a declared size was actually built.

## Acceptance

The gate runs and fails cleanly with every row still `planned`. A capacity
fixture that declares 500 and builds 0 fails with a message naming both numbers.
